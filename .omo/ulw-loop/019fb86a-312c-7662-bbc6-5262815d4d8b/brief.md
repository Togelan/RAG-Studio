# chat-reliability-streaming - Work Plan

## TL;DR (For humans)

**What you'll get:** Chat no longer fails on a fresh session or corrupts a session when you leave the page. Answers begin appearing from the provider as they are generated, while documents and previous chats remain safely preserved.

**Why this approach:** It first makes checkpoint persistence reproducible and compatible, then introduces genuine token streaming behind explicit cancellation and capacity limits. This keeps RAG grounding, citations, validation, and safety checks intact rather than trading them for a faster-looking UI.

**What it will NOT do:** It will not erase existing `rag-data`, expose secrets or internal tracebacks, or replace the present FastAPI/LangGraph/vanilla-JS stack.

**Effort:** Large
**Risk:** High - persistent chat state and streaming lifecycle both cross server/client boundaries.
**Decisions to sanity-check:** 10 simultaneous streams, one stream per session, `409` for same-session conflict, `503` plus `Retry-After` for global saturation, never persist a partial assistant answer.

Your next move: start the approved worker with `$start-work chat-reliability-streaming`, then run the requested `$ulw-loop` verification pass.

> TL;DR (machine): Large, high-risk reliability and genuine-streaming delivery with persistence compatibility, bounded load, and automated browser QA.

## Scope

### Must have

- Preserve and explain persistent documents/sessions; provide only explicit, non-destructive cleanup guidance.
- Reproduce and correct new-session checkpoint/state failures without exposing prompt text, keys, or traces.
- Implement true provider-token SSE without bypassing retrieval, grounding, validation, citations, or caching.
- Enforce 10 global in-flight streams in the single-process Docker deployment; reject a second stream for the same session with `409`; return `503` and integer `Retry-After` at global capacity.
- Ensure abort/navigation/session changes cancel safely, release capacity, prevent cross-session rendering, and never persist partial assistant output.
- Make the requested decision-evidence policy enforceable in canonical guidance and relevant roles.

### Must NOT have (guardrails, anti-slop, scope boundaries)

- No automatic deletion/reset of `rag-data`, Qdrant, raw uploads, SQLite, or existing sessions.
- No WebSocket replacement, new client framework, raw exception disclosure, unbounded queue/task creation, or real-key test traffic.
- No direct mutation of live SQLite for cleanup; retain a documented backup/reset operator procedure.

## Verification strategy

- Test decision: tests-after using pytest plus deterministic fake-provider socket integration and browser automation.
- Evidence: `.omo/evidence/chat-reliability-streaming/task-1.md` through `task-6.md`, plus final-verification evidence, generated by the worker; no human-only assertions.
- Required targeted proof: first true provider token arrives before completion; fragmented SSE is parsed; new and restarted Unicode sessions persist; cancellation/no partial persistence; same-session and global admission behavior; ten-session benchmark records p50/p95 TTFT, end-to-end p95, 429/503 count, active stream maximum, and RSS.
